## 2. Installed discord.py embed model

**CONFIRMED:** `discord.Message.embeds` is a list of `discord.Embed`. For each embed, `embed.title`, `embed.description`, and `embed.url` are optional strings. `embed.fields` is a list of proxies with `field.name` and `field.value`; `embed.author.name` and `embed.footer.text` are optional proxy attributes. Missing author/footer attributes read as `None` in the installed library. An offline 2.7.1 probe constructed a rich embed with title, description, fields, author, footer, and URL, then a `MessageSnapshot` from that embed's payload. The field names and values remained accessible through `snapshot.embeds[0].fields`. This demonstrates library deserialization, not what either real bot sends. See the [discord.py API reference](https://discordpy.readthedocs.io/en/stable/api.html#discord.Embed), [Discord embed structure](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx), and installed `discord/embeds.py` and `discord/message.py`.

**LIKELY:** If the pictured `Song`, `Artist`, or `Track` text is in a bot-supplied rich embed, it will be available in a description or field value. A bot could instead put all text in a title, author name, message body, image, interaction component, or client-generated preview. The visual examples do not establish which property contains each label or value. **UNKNOWN:** The actual payload shape and timing for BenjiBot and TaylorBot until a sanitized, consented gateway payload or controlled test is inspected.

The three data boundaries are distinct:

1. **CONFIRMED:** Text present in the received Discord embed object can be read locally without requesting Last.fm or another music service.
2. **UNKNOWN:** Text seen in the Discord client image may be rendered from an embed, component, image artwork, or later message edit. A screenshot does not prove the initial `MESSAGE_CREATE` payload contains it.
3. **CONFIRMED:** Information present only on the linked webpage would require a separate network request. Phase 2B should not make one.

## 3. Other bots, webhooks, intents, and permissions

**CONFIRMED:** `discord.Client.on_message` is called for created messages, including the client's own messages; the installed API has no general other-bot exclusion. `message.author.id` is the stable author ID, `message.author.bot` indicates a bot user, and `message.webhook_id` is set for a webhook-created message. The latter is separate from the author ID. Webhook messages can be received as messages; their names and avatars are presentation data, so they are unsuitable for identity or matching decisions. [discord.py events](https://discordpy.readthedocs.io/en/stable/api.html#discord.on_message), [discord.py Message](https://discordpy.readthedocs.io/en/stable/api.html#discord.Message), [Discord message object](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx).

**CONFIRMED:** `message.embeds` is empty for ordinary guild messages without effective Message Content access, subject to Discord's documented exceptions. MediaGuard already requests this privileged intent for attachments; Phase 2B needs no additional intent for ordinary received embeds. It still depends on the intent being enabled or approved for the application where Discord requires that. Guild Messages delivers `MESSAGE_CREATE`; View Channel allows access to the protected channel, and Manage Messages remains necessary for deleting someone else's message. Reading a new gateway event does not require a second connection, a Last.fm permission, or Read Message History. Sending a Detection notification still needs View Channel and Send Messages in its destination. [Discord message-content policy](https://support-dev.discord.com/hc/en-us/articles/6207308062871-What-are-Privileged-Intents), [discord.py events](https://discordpy.readthedocs.io/en/stable/api.html#discord.on_message), [Discord permissions](https://discord.com/developers/docs/topics/permissions).

**LIKELY:** An ordinary, non-ephemeral guild message made by a third-party bot or webhook in a visible protected channel will reach this `on_message` handler. **UNKNOWN:** Whether the two examples are ordinary message-create embeds, delayed edits, ephemeral interaction responses, or other UI forms. Do not key behavior to bot names or IDs.

## 4. Forwarded embeds

**CONFIRMED:** Discord's forward snapshot schema currently includes `embeds`; it excludes the original `author`, supports one snapshot at present, and fixes the snapshot at forwarding time. `discord.py` 2.7.1 turns each snapshot embed into `discord.Embed` via `Embed.from_dict`. Thus fields are inspectable when they are present in `message.message_snapshots[n].embeds`. The forwarded message's `message.author` is the person or bot that forwarded it, not a reliable identity for the original bot. [Discord snapshot and forwarding specification](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx), [discord.py MessageSnapshot](https://discordpy.readthedocs.io/en/stable/api.html#discord.MessageSnapshot).

**LIKELY:** A forwarded rich bot embed whose metadata was present at forwarding time can use the same textual inspection function as an ordinary embed. **UNKNOWN:** Whether the two specific bots' content is preserved as snapshot fields in practice. A forward made before an embed arrives, a forward with no snapshot metadata, or visually rendered content outside `embeds` cannot be assumed inspectable. Do not fetch the original message or invent a fallback; mark absent required metadata as unavailable for this inspection path. A forward's audit identity should name the forward sender and current message, with source `forwarded_embed`.

## 5. Narrow deterministic matching boundary

The smallest useful Phase 2B candidate is an opt-in, per-guild list of explicit blocked phrases. It should inspect only Discord-exposed text in `embed.title`, `embed.description`, and `embed.fields[].value`, on ordinary message embeds and forwarded-snapshot embeds. This covers a field value such as `because i liked a boy` or `Tenderness` if the bots actually put the text there. The same matching function should handle either bot without identifying the provider. **LIKELY** is the expected usefulness; only the API surface is **CONFIRMED**.

Do not match `field.name` by default: labels such as “Song,” “Artist,” and “Track” are generic and create false positives. Defer `embed.author.name` and `embed.footer.text` initially because they commonly contain bot branding, usernames, or counters; a sanitized real payload could justify adding a specific surface later. Do not inspect `embed.url`, author/footer icon URLs, image or thumbnail URLs, attachment URLs, artwork, provider URLs, `message.content`, or external webpages. If a selected text surface contains a URL or Markdown link, exclude the URL target from matching; the visible label can be treated as text. Never fetch, store, or notify with the URL.

Use literal, whole-phrase matching *within one text surface*, not regex supplied by a moderator and not a substring inside another word. Normalize both configured phrases and candidate text with Unicode NFC, `casefold()`, and whitespace collapse. Require Unicode letter/number boundaries at phrase edges; preserve punctuation and diacritics. Do not join separate fields or use stemming, fuzzy similarity, confusable folding, or AI. For example, a configured `Tenderness` can match `Tenderness` in a field, but should not match `Tendernesses`; a two-word term should appear contiguously after whitespace normalization. Case and composed/decomposed Unicode differences should not change results. Short or generic terms, especially common artist names, remain a moderator configuration risk. Exact field equality is safer but misses descriptions such as `Song: ...`; bounded whole-phrase search is the practical middle ground. These are **RECOMMENDATIONS**, not implemented behavior.

**CONFIRMED:** Discord limits rich embed title, description, fields, and combined embed text, with up to 25 fields and a 6,000-character combined textual limit across message embeds. [Discord embed limits](https://github.com/discord/discord-api-docs/blob/main/developers/resources/message.mdx). Phase 2B should still enforce its own small bounds: at most 10 embeds, 25 fields per embed, 6,000 candidate characters per message, and a bounded number and length of configured terms. Skip malformed/non-string values safely. An exceeded inspection bound should be treated as unavailable, never as an approval or a reason to delete. Stop at the first deterministic match; retain only the configured term's stable identifier. Multiple matching terms must still produce one deletion and one audit event.

## 6. Loop safety and timing

**CONFIRMED:** The current author-ID equality check prevents MediaGuard from inspecting or deleting its own Detection notification when `client.user.id` is known. `author.bot` cannot be used as a blanket exclusion because it would discard the target messages. A Phase 2B embed path should keep the self-ID check at the start of `handle_message`; if the connected self ID is unavailable, fail closed for embed enforcement until it is known. A webhook impersonating MediaGuard's display name is not the same identity. Other bots or webhooks that repost MediaGuard output are new messages and cannot be safely exempted based on name or broad bot status. Keep future notifications free of the raw blocked phrase and use a rule identifier, reducing accidental feedback loops.

**CONFIRMED:** The code only reacts to `on_message`. Discord can add or alter embeds on `MESSAGE_UPDATE`, and discord.py documents that embed-server updates may arrive inconsistently. Consequently a create-only Phase 2B can miss delayed URL previews and bot edits. [discord.py edit event](https://discordpy.readthedocs.io/en/stable/api.html#discord.on_message_edit). **RECOMMENDATION:** Defer edit handling from the first Phase 2B increment and state this coverage limit plainly. If real bot examples prove edits are essential, investigate a narrowly scoped edit handler and its cache/raw-event behavior before claiming reliable coverage. Do not fetch or crawl to compensate.

Malformed/missing fields, no snapshot, multiple embeds, and large payloads must have defined safe outcomes. A failed embed inspection must not be converted to a `MATCH`. A separate attachment match may still follow the existing attachment precedence. Preserve the message-ID reservation so duplicate create deliveries, multiple matches, and later events cannot trigger a second delete.

## 7. Reuse and minimum persistence

**CONFIRMED:** The existing delete, audit reservation, outcome, and post-deletion notification sequence can be shared. Its current result and presentation structures are audio-specific: `InspectionResult` carries `media_type`, `Database.reserve_enforcement` writes a non-null `media_type`, `blocked_audio_embed` indexes an audio-name map, the dashboard labels sources only `direct`/`forward`, and Overview counts confirmed deletions as audio blocked. Passing an embed match directly into that sequence would mislabel or fail. A small future refactor should allow an attachment or embed inspector to supply a common match decision with kind/source and an identifier, then use the same single-delete sequence with kind-specific notice wording. Define deterministic precedence when one message matches both paths; never delete twice. This is a **RECOMMENDATION**; Phase 2A makes no code or schema change.

For an embed deletion, minimal durable facts are guild, channel, current message, and forwarding author IDs; optional presentation names; detection kind and source (`embed` or `forwarded_embed`); stable configured rule ID; detection time; deletion state and confirmed UTC deletion time; notification state. The configured phrase can remain in the separate configuration record and need not be copied into audit or the Detection notification. A future Detections UI can show “Blocked term” and the rule identifier plus current metadata and outcomes. Do not retain the whole embed, artwork, body, URLs, attachment bytes, matched text excerpt, or the original forwarded author's identity (absent from the snapshot). **LIKELY:** These facts are sufficient for the existing audit and manual log correlation purpose, subject to product review of rule renaming/deletion and what the UI should show for a retired rule.

## 8. Phase 2B test plan

Use synthetic `discord.Embed` and `MessageSnapshot` objects and the current fake message/channel boundary; no token or live server. Test the pure text selector and normalizer separately from one-delete enforcement.

| Area | Cases and expected boundary |
| --- | --- |
| Basic intake | User message without embed: no embed match. Other bot with matching versus nonmatching field: match only the former. Bot identity changes without changing the result. |
| Loop and webhook | MediaGuard's own notification: never inspected/deleted. Third-party webhook embed: evaluated under the same rules; `webhook_id` and display name do not grant exemption. Other bot reposting a notification: no match unless it independently contains a configured phrase. |
| Text selection | Multiple embeds and fields; title, description, field value; generic field name alone, footer, author, image URL, embed URL, link target, and attachment URL do not match. Missing/null values are skipped safely. |
| Determinism | Case differences, NFC composed/decomposed Unicode, whitespace, exact phrase, phrase inside longer text with valid boundaries, partial-word false positives, punctuation, and separate fields that must not be concatenated. |
| Bounds | Maximum valid embed, over-limit synthetic embed, many fields/embeds, long configured term list, and malformed payloads finish within the cap. Incomplete inspection never deletes. |
| Forwarding | Snapshot with a matching rich embed field; snapshot with no embeds or unavailable metadata; forward sender is the audit author. Test nested/extra snapshots conservatively within the documented depth. |
| Phase 1 regressions | Direct and forwarded audio matches still delete once; ordinary `SAFE` and `UNAVAILABLE` retain their meanings; audio plus embed match yields one chosen result and one deletion. |
| Enforcement | Deletion failure is not “Deleted”; notification failure does not undo successful deletion; duplicate event and restart do not retry an ambiguous deletion; multiple terms cause one audit row and one notification. |
| Privacy | Audit, API response, and Detection embed contain no entire source embed, message body, image/attachment bytes, URL, CDN link, base64 payload, or temporary path. |
| Timing | A create event without a later embed does not trigger an edit-path action. Edited messages are explicitly deferred in the first increment and documented as a coverage limit. |
